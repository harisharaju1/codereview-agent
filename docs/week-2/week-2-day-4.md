# Day 4 — The Agent Loop

## What was built

- **`src/schemas/pull_request.py`** — `PullRequestDetail` (`number`, `title`, `head_sha`), the shape needed to know which exact commit to fetch files at.
- **`src/services/pull_requests.py`** — `fetch_pull_request_metadata`, calling the same URL `fetch_pull_request_diff` already uses but with the default JSON `Accept` header instead of the diff media type, to get the PR's head SHA. (Named `fetch_pull_request` in the plan doc; renamed during review for clarity — see the plan doc for the original name.)
- **`src/services/review_agent.py`** — the agent loop itself:
  - `TOOL_DEFINITIONS`: five hand-written tool schemas (`get_file_content`, `search_codebase`, `check_dependency_versions`, `run_linter`, `submit_review`) sent to Claude on every request.
  - Four executor functions (`_execute_get_file_content`, `_execute_search_codebase`, `_execute_check_dependency_versions`, `_execute_run_linter`), each bridging the narrower agent-visible arguments to the real Week 2 service functions, dispatched via `_TOOL_EXECUTORS`.
  - `run_review_agent`: fetches the PR + diff, then loops — call Claude, execute whatever tools it requested, feed results back — until a validated `submit_review` call returns the findings, or `MAX_ITERATIONS` (8) is exhausted.
- **`src/routers/review.py`** — `POST /github-app/repos/{owner}/{repo}/pulls/{number}/review`, synchronous, scoped through the same installation-auth chain as every other route.
- **Tests**: `test_review_agent.py` (loop mechanics, via a duck-typed fake Anthropic client — no real API calls) and `test_review_agent_executors.py` (the four executors tested directly, in isolation) — 10 new tests.

## Why it's built this way

- **The agent-facing tool contract is deliberately narrower than the underlying Python function signatures.** `run_linter`'s real signature is `(path, content)`; the agent only ever sees `{"path": string}` — the executor fetches `content` itself, since asking the model to supply an entire file's text as a JSON argument would be wasteful and would defeat the purpose of having a `get_file_content` tool at all (the model would need to already have the content to send it). `get_file_content`, `search_codebase`, and `check_dependency_versions` all close over `client`, `installation_token`, `owner`, `repo` the same way — none of those are things the model should see or control, least of all a credential.
- **`submit_review` is a real tool, not the model's final plain-text reply.** A `ToolUseBlock`'s `input` validates against the JSON schema it was given far more reliably than asking the model to "reply in this format" as text, which regularly gets wrapped in markdown fences or subtly malformed. This is what lets `ReviewFinding` validation apply directly to `tool_use.input`, with zero text-parsing in between.
- **A validation error on `submit_review`'s input is fed back to the model, not treated as a hard failure.** The same "let it self-correct within a bounded budget" idea `github_retry.py` already uses for a flaky network call, applied here to a model producing malformed structured output instead.
- **Every tool executor's exceptions are caught broadly and turned into an `is_error` tool result, not allowed to crash the loop.** A failed tool call (a GitHub 404, a subprocess issue) is information the model can react to — trying a different approach, or noting it couldn't check something — not a reason to fail the entire review over one bad call.
- **Parallel tool use is handled correctly, not assumed away.** One assistant turn can contain multiple `tool_use` blocks, including — in principle — `submit_review` alongside a genuine data-fetching tool in the same turn. The loop always finishes building a `tool_result` for every block in a turn before returning, even once `submit_review` is found, since every block requested in one turn needs exactly one corresponding result in the same next message.

## Alternatives, Patterns, and Architecture Decisions

**Real deviation from the plan, found while writing the code, not while planning it:** the plan document (`week-2-day-4-plan.md`) explicitly said `get_file_content`'s agent-facing schema would include `ref` as a parameter (`{"path": string, "ref": string}`), closing over only `client`/`installation_token`/`owner`/`repo`. While actually writing `TOOL_DEFINITIONS`, this turned out to be the wrong call: there is exactly one correct ref for an entire review — the PR's head commit — and nothing else in this design (no "base branch" tool, no cross-commit comparison tool) gives the model a legitimate second ref to ever supply. Exposing `ref` as a free-text argument would only ever invite a hallucinated or stale SHA, with no corresponding benefit. The actual implementation closes over `ref` for both `get_file_content` and `run_linter`, making them consistent with each other (the plan already had `run_linter` closing over `ref` — this just extended the same reasoning to the one tool the plan had inconsistently left it open on). Recorded here explicitly rather than silently diverging from the plan doc without a trace, matching this project's own standing practice (the same as Day 3's `dotnet format analyzers` → plain `dotnet format` correction).

**Pattern: a uniform executor signature, even where several parameters go unused by a given executor.** Every executor is `(client, installation_token, owner, repo, ref, arguments) -> str`, even though `_execute_search_codebase`'s real service call has no notion of `ref` at all. The alternative — a bespoke signature per executor matching exactly what each one needs — would be marginally more precise but would break the one thing that makes `_TOOL_EXECUTORS` a clean dict lookup: every value in that dict needs to be callable the same way from the loop, without the loop needing to know which specific parameters a given tool actually uses. A small, known amount of unused-parameter noise per executor was judged worth that uniformity.

**Decision: `messages` is built from plain dicts throughout, not constructed `anthropic.types` objects — except for `response.content`, which gets appended directly as the SDK's own objects.** This is a deliberate asymmetry, not an inconsistency: Anthropic's own documented pattern (confirmed via the compaction example in Anthropic's SDK docs) is to append `response.content` unchanged, since re-serializing it into dicts by hand risks silently dropping fields (like compaction blocks, when that feature is in play) the SDK itself knows how to round-trip correctly. Everything *this project* constructs from scratch (the tool-result messages) is built as plain dicts, since there's no SDK convenience type to lean on for those and dicts keep the loop's own data visible and easy to inspect/test.

**Decision: two distinct exception types (`AgentDidNotSubmitReviewError`, `AgentExceededMaxIterationsError`) instead of one generic failure.** These mean genuinely different things to whoever is debugging a failed review — "the model gave up talking without ever calling submit_review" versus "the model kept calling tools past the budget this project allows." Both currently surface as the same `502` from the router (Day 4 didn't need finer-grained HTTP status differentiation yet), but the distinction is preserved in the exception types themselves for whenever logging or monitoring wants to tell them apart — cheap to keep separate now, would require re-deriving the distinction later if collapsed into one exception today.

**Considered and rejected: forcing `tool_choice` to `submit_review` on the final allowed iteration**, discussed as an idea before building (see the conversation that led to this plan) as a way to get a best-effort review instead of a hard `MAX_ITERATIONS` failure. Not built this day — the plan as reviewed and approved used the simpler "raise a clear error" behavior, and adding the forced-`tool_choice` variant wasn't part of what was actually signed off on. Worth revisiting as a real, scoped follow-up, not forgotten — noted here so it isn't lost.

## Python-specific things worth calling out

- **`@dataclass`-based fakes for testing, not `unittest.mock.Mock`.** The fake `FakeToolUseBlock`/`FakeMessage`/`FakeAnthropicClient` classes in `test_review_agent.py` are plain dataclasses with real attributes, not `Mock` objects with attributes bolted on dynamically. This means a typo in a fake's field name fails immediately and loudly (an `AttributeError` or a dataclass construction error) rather than silently returning a `Mock` object that happens to satisfy `hasattr` checks — a real advantage over `Mock` for this specific case, where `review_agent.py`'s code accesses a small, fixed set of real attributes.
- **Duck typing is what makes the fakes work without touching the real `anthropic` SDK types at all.** `review_agent.py` never checks `isinstance(block, anthropic.types.ToolUseBlock)` — it only ever accesses `.type`, `.name`, `.id`, `.input`. Any object with those attributes works, which is precisely what let the test fakes skip constructing (and satisfying the internal validation of) real SDK response objects.
- **`except Exception as exc:` with a `# noqa: BLE001` comment** — deliberately broad, and flagged as deliberate in a comment specifically because "catch everything" is usually a code smell this project would otherwise avoid (see `github_app_auth.py`'s narrower `except httpx.HTTPStatusError` for contrast). Here it's correct: a tool executor can fail in genuinely unpredictable ways (a `KeyError` from malformed arguments, a subprocess issue, an HTTP error), and *all* of them need the same treatment — visible to the model as a tool error, not a crash.

## .NET parallel

- The tool-call loop (send messages, inspect for function-call requests, execute, append results, resend) is structurally identical to Semantic Kernel's or Azure OpenAI's function-calling loop in .NET — the shape isn't Anthropic-specific, it's how every major LLM tool-calling API works underneath each SDK's own wrapper.
- Feeding a `ValidationError` back into the loop for the model to self-correct ≈ a resilient API returning a structured 400 a *retrying client* could act on — except here the retrying client is the model itself, inside the same request/response cycle, not a separate outer retry policy.
- The executor-function layer (agent-visible tool ≠ underlying service function) ≈ a controller action's DTO being intentionally narrower than the domain service method it calls.
- Two distinct, named exception types for two different failure modes ≈ the same instinct behind defining `OrderNotFoundException` and `OrderAlreadyShippedException` separately in a .NET domain layer, rather than one generic `OrderException` — costs nothing to keep distinct, and the distinction is exactly what a caller further up the stack might eventually want to act on differently.

## Learning Notes: Similarities to Prior Work

Private cross-reference only — doesn't affect anything above.

- **This is the first genuinely LLM-driven control flow in either this project or the earlier TypeScript project.** Every prior piece of logic in both projects is deterministic — given the same input, the same code path runs every time. Which tools get called, how many times, and in what order is now decided by the model at runtime, which is exactly why the fake-client testing approach exists: correctness here means "the loop mechanics are right for any sequence of model decisions," not "this one specific path is right."
- **The executor layer narrowing what's exposed to the model** is a new, concrete instance of the same DTO-narrower-than-service-method instinct this project's router/service split has followed since Week 1 — now applied to an LLM's view of a function instead of an HTTP caller's.
- **Finding and recording a real deviation from the plan mid-build** (the `ref`-closure decision) continues the exact same practice Day 3 established with the `dotnet format analyzers` discovery — this project's plans are treated as a considered first guess, not a contract, and when reality disagrees with the plan, that disagreement gets written down rather than silently absorbed.
