# Day 3 — `run_linter` (Python, TypeScript/JavaScript, C#)

## What was built

- **`src/schemas/lint.py`** — `LintFinding` (`file`, `line: int | None`, `column: int | None`, `rule: str | None`, `message`, `severity: str`) and `LintResult` (`supported: bool`, `findings: list[LintFinding]`).
- **`src/services/linters/python_linter.py`** — `run_ruff`: writes the file to a temp dir, runs `ruff check --output-format=json --isolated` against it, parses the result.
- **`src/services/linters/js_ts_linter.py`** — `run_oxlint`: same shape, running `oxlint --format json` (added as a runtime dependency via `uv add oxlint` — a zero-config, single-binary linter with a PyPI wheel wrapper, no Node.js required).
- **`src/services/linters/csharp_linter.py`** — `run_dotnet_format`: scaffolds a throwaway, dependency-free `.csproj` around the single file in a temp dir, runs `dotnet format --verify-no-changes --report`, parses the structured report.
- **`src/services/linters/dispatch.py`** — `run_linter`, the fourth and final tool: dispatches to the correct linter by file extension via a dict, returning `LintResult(supported=False, findings=[])` for anything unrecognized.
- **Tests**: `test_linters.py` — 4 tests, all invoking the *real* `ruff`, `oxlint`, and `dotnet format` binaries (not mocked subprocesses), skipped automatically if the .NET SDK isn't installed.

## Why it's built this way

- **All three linters take input the same way: written to a real temp file, not `stdin`.** `ruff` genuinely supports `--stdin-filename`, but `dotnet format` needs a real project on disk and this installed `oxlint` version has no stdin flag at all — giving all three the identical "write, invoke, clean up" shape means `dispatch.py` never has to special-case how one language's tool receives input differently from the other two.
- **`ruff` runs with `--isolated`.** Without it, ruff would walk up the temp directory's parents looking for a `pyproject.toml`/`ruff.toml` to apply — and could, depending on exactly where the OS placed the temp dir, silently pick up *this project's own* lint config (100-char line length, this project's specific rule selection) and apply it to someone else's reviewed code. That's not a rule set that has any business being imposed on an arbitrary external repo.
- **`oxlint`, not ESLint.** ESLint's plugin/parser resolution assumes a real project context (a `package.json`, installed plugins, a resolvable config) that doesn't exist for one isolated file's content. `oxlint` genuinely works with zero project context. The real, accepted cost: it implements a meaningful but not exhaustive subset of ESLint's rules, and applies none of a real repo's own ESLint config — it reports what its own built-in rule set catches, not "everything that repo's actual lint setup would have caught."
- **`run_linter`'s unsupported-extension case returns a structured `LintResult(supported=False)`, never an empty findings list and never an exception.** An empty list is genuinely ambiguous (clean code vs. no linter exists) — collapsing those into one shape would silently misreport "we didn't check this" as "we checked, it's fine."

## Alternatives, Patterns, and Architecture Decisions

**The plan's original command choice for C# turned out to be wrong, discovered by actually testing it before writing any code.** The Day 1 week plan called for `dotnet format analyzers --verify-no-changes`. Tested directly, against a file with an obvious, real formatting problem (inconsistent brace placement, `int x=1;` missing spaces): `dotnet format analyzers` returned an *empty* report. So did `dotnet format style`. Only `dotnet format whitespace` caught it — because `analyzers` and `style` cover exactly what their names say (analyzer diagnostics, IDE-style rules) and neither category includes plain whitespace/formatting issues, which is realistically the most common thing worth flagging in an isolated file with no real project context around it. Rather than juggle three subcommands with three separate report shapes, the final implementation uses plain `dotnet format` with no subcommand — which runs all three categories together against one unified report. This is recorded here deliberately, not silently fixed without a trace, because it's a genuine example of "the plan's best guess, made without the tool actually running, turned out to be wrong" — worth knowing as a pattern (verify a specific CLI invocation's actual behavior before committing a design to it) more than as a C#-specific fact.

**Decision: the scaffolded `.csproj` deliberately has zero `<PackageReference>` items.** A real C# file being reviewed would almost certainly come from a project that references *something*. Scaffolding with no dependencies at all is a real, accepted tradeoff: it's what keeps `dotnet format`'s implicit restore step fast (nothing to fetch from NuGet over the network — confirmed at ~2 seconds per invocation with an empty project, against no direct comparison available for what a real restore with actual packages would add, but plausibly much more given network I/O). The cost: any analyzer diagnostic that depends on resolving a symbol from a referenced package won't fire correctly, or may misfire, against otherwise-valid code. Whitespace and style diagnostics — the categories `dotnet format` was specifically confirmed to catch above — don't depend on symbol resolution at all, so they're unaffected. This tradeoff was made deliberately, with the specific limitation it introduces named explicitly, rather than discovered later as a surprise.

**Pattern: dict-based dispatch table for `run_linter`, directly contrasted with Day 2's `if/elif`-based dispatch for `check_dependency_versions`'s manifest handling.** Every branch of `run_linter`'s dispatch has the *exact same shape* — one extension maps to exactly one `(path, content) -> list[LintFinding]` function. That uniformity is precisely what makes a dict simpler than the alternative: a fourth language later is one new dict entry, nothing else changes. `check_dependency_versions`'s dispatch lacks that uniformity (each branch needs a different ecosystem label bundled with a different parser *and* a different registry function — three things, not one), which is why that dispatch stayed an `if/elif` chain. Two structurally similar-looking decisions, in the same week, landing differently for a real, statable reason each — this is the kind of side-by-side comparison worth calling out explicitly, per this project's new standing practice (see Day 1's memory note on verbose reasoning), rather than leaving a reader to wonder why the codebase isn't consistent.

**Real subprocess invocation in tests, not mocked, was a deliberate choice — and a real cost.** `test_linters.py` calls actual `ruff`/`oxlint`/`dotnet` binaries. This means these specific tests are meaningfully slower than the rest of the suite (the `dotnet format` one alone: roughly 2 seconds, versus sub-millisecond for most of this project's mocked tests) and require all three tools genuinely installed to run at all — the C# test is skipped automatically (`pytest.mark.skipif`) if `dotnet` isn't found, rather than failing confusingly in an environment that hasn't done the Day 3 manual setup step yet. The alternative — mocking `asyncio.create_subprocess_exec` and hand-writing fake JSON matching each tool's documented output shape — would be faster and require no local tooling, but would only prove this project's *parsing* code agrees with what a test author *assumed* each tool prints, never confirming it against what the tools *actually* print. Given none of these three tools' output formats were previously used in this project, and one of them (`dotnet format`'s report shape) had to be empirically discovered rather than looked up cleanly in docs, testing against the real thing was judged worth the cost this time.

## Python-specific things worth calling out

- **`asyncio.create_subprocess_exec` + `.communicate()`, not `subprocess.run()`.** This project is async throughout — every GitHub call already goes through an async `httpx` client. A blocking `subprocess.run()` call inside an `async def` function would stall FastAPI's entire event loop for the duration of the lint (up to ~2 seconds for the `dotnet` path), blocking every other concurrent request this process is handling, not just the one that triggered the lint.
- **A non-zero exit code from `ruff`/`dotnet format` is expected, normal behavior**, not a signal of a broken subprocess call — both tools exit non-zero specifically *because* they found something to report. This project's code deliberately doesn't check the return code as its primary signal; it reads structured output (`stdout` JSON for ruff/oxlint, a report file for dotnet format) instead, and treats a *missing or malformed* output as the real "something actually broke" signal.
- **`pytest.mark.skipif(shutil.which("dotnet") is None, ...)`** — a standard `pytest` pattern for making a test's environmental prerequisite explicit and self-documenting, rather than letting it fail with a confusing subprocess error in any environment that hasn't done the Day 3 setup step.

## .NET parallel

- Scaffolding a throwaway `.csproj` and running `dotnet format` against it is closer to a CI pipeline step than typical application code — the same idea as a build pipeline's `dotnet format --verify-no-changes` lint gate, just triggered by this service at request time instead of by a CI runner on every push.
- The dict-based dispatch table (extension → linter function) ≈ a `Dictionary<string, Func<...>>` used as a strategy-pattern lookup in C# — the same shape, same reasoning (uniform branches, easy to extend), just Python's dict standing in for .NET's generic dictionary.
- `--isolated` (ruff) and the deliberately dependency-free scaffolded `.csproj` (C#) are both instances of the same idea: explicitly preventing a tool from picking up ambient configuration/context it would otherwise search for — the same category of concern as making sure a `dotnet test` run in CI doesn't accidentally pick up a developer's local `NuGet.Config` pointing at a private feed.
